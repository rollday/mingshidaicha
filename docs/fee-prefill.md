# 费用预填与现金流核对

## 目标与接口

核对页在有充分原文依据时预填费用计入方式，保留用户修改和确认。目标是减少重复填写，同时避免把“一并扣划”误解成“已经包含在所填还款额中”。

计算接口继续使用 `included_in_cashflows: true | false | null`，配合 `timing`：

| 解释 | 所填金额口径 | 计算处理 |
| --- | --- | --- |
| 已含在还款额中 | 所填还款总额已包含该笔费用 | 不重复加收 |
| 已从到账净额扣除 | 所填到账已经扣掉该笔费用 | 不重复扣款 |
| 另行支付 | 费用尚未反映在所填到账或还款额中 | 按收费期加入现金流 |
| 待确认 | 原文不足、冲突或金额无法对应 | 暂不输出最终年化 |

保留现有接口是为了兼容手工输入、显式还款计划、到期及指定期费用；仅替换成四个枚举并不能证明费用是否已经体现在某个金额中。自动建议另附 `treatment / rule_id / reason / evidence_ids`，计算结果另附逐项费用账本和逐期核对结果。

## 自动预填的证据要求

模型先提取逐字原文，后端验证摘录确实存在，再由 `shared/fee-prefill.ts` 生成建议。建议不能来自模型自报的置信度。没有规则支持的模型 `true` 和 `false` 均恢复为 `null`；手工录入和用户明确修改不经过这一模型抽取流程。

- **具名另收**：所选每期金额与原文相同，原文明确该笔具名、具金额费用在此之外另付，或明确不包含该费用，才预填另收。
- **具名已含**：费用名称、金额、所选含费还款总额都能对应，且多项已含费用的合计不能超过相应金额。
- **放款扣除**：原文明确扣除具名费用后的净到账，且与所选到账一致；已扣费用合计不能超过本金与到账的差额。不能把所有一次性收费都视为从放款中扣除，混合扣费与另付分别处理。
- **有限条件的 A1**：仅针对无显式计划、按月标准等额本息，且本金、还款额、完整期数、周期、方式、合同利率都有独立明确证据时，用 BigInt 有理数独立算本息并按分取整。理论本息与所选还款额一致、原文另列正常每期费用、无包含或其他冲突，才支持另收。
- **阻断条件**：否定、假设、例子、相反收费描述、不同金额、同名费用无法区分、补贴减免、尾款、逾期或综合利率等，不得被当成标准 A1 证明。仅“一并扣划”“不同渠道扣收”不能决定计入方式。

A1 不使用“把所选还款额传进计划生成函数再取出来”的循环论证。数字必须绑定对应语义，不能用“本金18000、担保最高金额20000”中的20000证明本金。

## 交互与留痕

可靠建议在初次抽取后自动应用，并显示来源。金额补充完整后，也可点击“按合同条款预填含费状态”；该操作只填写未被人工编辑的待确认项。提交时后端重新验证本次采纳的费用 ID，拒绝失效的预填声明。

影响年化的待确认费用优先展开，已确认费用、或有费用和其他背景信息折叠但仍可编辑。每笔费用可查看原文并定位原页。只改变显示顺序，不重新排序事实数组；删除或重排时，用稳定 `fee.id` 对齐证据和更正记录。

修改到账、还款、利率、期数或费用基准会清空依赖旧基准的自动状态，要求重新核对。服务端分别记录自动采纳和人工覆盖，重新打开案件后仍能正确区分。网页报告及 PDF 保存预填来源和用户修改前后值；历史预填不代表修改后的金额仍已得到原文支持。

## 计算核对及其边界

`python/loan_plan.py` 为每笔费用生成发生期和唯一归类：到账已扣、还款已含、另付、或有。计算前核对独立构造的另付费用行，计算后按期对照 IRR 实际现金流：

```text
放款期净现金流 = 所填到账 − 尚未计入的放款期费用
以后各期净现金流 = −(该期所填还款 + 该期另付费用)
预计实际支付 = 所填还款计划合计 + 另付费用合计
总成本 = 预计实际支付 − 所填到账
```

已含费用超过对应还款额、已从到账扣除的费用超过本金到账差额，或者账本与现金流不一致时，返回 `CALCULATION_INCONSISTENT`。已知标准等额本息合同利率时，还独立检查“本息＋已含费用”是否装得进还款额，并允许计划的分舍入尾差。

这些检查验证归账与算术一致性，不能替代原文真实性或费用清单完整性。没有可靠合同利率时，不强制反推出本息；不能用同一组错误现金流倒算利息，再称守恒等式证明了没有漏费。也不要求所有案件满足“本金−全部一次性费用＝到账”，因为其中可能有另付费用。

## 回归口径

以下为依参数构造的合成场景，不代表已经验证某份原合同文件：

| 场景 | 现金流或预期 |
| --- | --- |
| v2 参数：本金20000，放款费用600＋499＋30，每期本息913.69，另收120＋88，24期 | 净到账18871，每期支出1121.69；名义年化36.739117%，总成本8049.56 |
| v3 参数：本金20000，一次性扣4441，24个月各还913.69 | 净到账15559；名义年化35.389361% |
| 同一笔真实已含费用与另付表示 | 两种合法输入产生相同现金流，不重复计费 |
| 只有“一并扣划”，缺少完整本息证据或金额 | 保留待确认 |
| 正反证据冲突、否定周期、错绑金额、逾期利率 | 不生成错误预填 |
| 修改基准、保存后重开、费用删除和排序 | 预填正确失效，人工修改保留，证据不串项 |

“每期1121.69已含88”本身不足以确定22.53%的年化，缺少到账和其他现金流条件，因此不将该数值硬编码为验收目标。

## 静态资源交付

Node 静态路由按 `Accept-Encoding` 协商 Brotli/gzip，合并 `Vary`，对 GET/HEAD 提供 ETag 和304响应。压缩结果按文件变化失效并限制缓存数量及单文件大小。

- Vite 带内容哈希的资源：`public, max-age=31536000, immutable`。
- HTML及不带哈希的静态资源：`no-cache`，允许存储但使用前重新验证。
- API、会话、上传材料与报告接口：继续 `no-store`。

反向代理可能覆盖响应头，因此部署后须检查实际服务域名的 `Content-Encoding / Cache-Control / Vary / ETag`。本地修复和测试通过不等于线上已更新。滚动部署时应保留仍被旧页面引用的旧哈希资源。
